### How the work runs

As in step 1 ([STEP1.md](STEP1.md), Handoff): Opus writes a slice's full brief here, commits it, and hands it to **one Sonnet subagent**; Sonnet implements and commits on branch `1.0` (never pushes) and reports; Opus reviews and brings every gap to the owner with a recommendation; the owner decides; the decisions go into `docs/design/` and become the next brief's first tasks. Commit after every round.

New in step 2: **a slice is sized to fit one Sonnet session** (about the work of slice 1f, some 150k tokens), and the brief is written to keep that session small (see "Rules for every slice"). From 2d on, the owner's review is in the browser: the slice ends with screenshots to compare against the Design canvas (<https://claude.ai/artifact/HPX2k7wM7ENHVQLc3zzjL5>; read it back before relying on it).

## Slice 2k3: the type order, the key grouped by type, and a `vi` key's numbers

The owner's changes after 2k2 (items 68 and 69): a quiz can declare that its question types come in a set order (`type_order`: `none`, `by-section`, `by-quiz`); `check` holds it to that order and a profile can require one; `shuffle_questions` keeps the order; the key's other answers are grouped by type; a numeric answer in a key is written in the paper's number format. The tests that matter: **a quiz without `type_order` gives the same plans, pages and papers, byte for byte, as before this slice**; **a quiz with an order and `shuffle_questions` keeps every question in its group for every seed**, on the page and on the paper; **the rule finds a quiz out of its declared order, says where, and `require` finds a quiz that declares too little**; **a `vi` key writes "0,4"**.

### Decided for this slice

- **1. A `vi` key's numbers** (owner, item 68). A numeric answer in a key or `inline` (the value, its tolerance, its range) is written in the paper's number format, as points are: "0,4 (± 0,001)" in `vi`, "0.4 (± 0.001)" in `en`. A `short` or `blanks` answer is text and prints as written.
- **2. The front-matter key `type_order`** (owner; the details **to approve**):
  ```yaml
  type_order: by-section        # none (default) | by-section | by-quiz
  ```
  or the long form, with the quiz's own order:
  ```yaml
  type_order:
    by: by-quiz
    order: [[single, multi], truefalse, [matching, ordering], blanks, [short, numeric, fields], code, essay]
  ```
  - **The order** is a list whose items are a type or a list of types that may mix (a *group*). The default is the owner's: `[[single, multi], truefalse, [matching, ordering], blanks, [short, numeric, fields], code, essay]`. Types not in the order (`scale` in the default) may stand anywhere.
  - **`by-section`:** in each `#` section, the questions' groups never go back to an earlier group. **`by-quiz`:** the same over the whole quiz in source order, across sections. A quiz without sections is one section, so there the two are the same. `none` is as if the key were absent.
  - **Bad values** are `syntax.value` with the line, as any front-matter key: an unknown `by`, an unknown type, a type in two groups, an empty `order`, `order` without `by`. An unknown key in the long form is `syntax.unknown-key`.
  - It is part of the quiz, so it is in `quizHash`; a quiz without it keeps its hash (test it).
- **3. The shuffle keeps the order** (owner; how, **to approve**). When `type_order` is not `none` and `shuffle_questions` is on, `planFor` shuffles each section's questions only inside each *run*: a stretch of consecutive questions in the same group (a type outside the order is a run of its own and does not move). Runs keep their places, so a quiz in its order stays in it, on the page and on the paper, whichever the mode (sections never move and a question never leaves its section). Shuffling by runs, not by sorting into groups, means a quiz out of its order is shuffled without being rearranged: `check` reports it, the plan does not fix it. A `pick` bank draws first, as now, then the runs are shuffled. The random stream stays `seed`, `questions`, the section id, drawn run after run. **A quiz without `type_order` gets exactly today's plan**: the test covers every fixture with `shuffle_questions` and two seeds.
- **4. The rule `questions.type-order`** (owner; the details **to approve**). A quality rule, **warning in `default`** (it is silent on a quiz that declares nothing, so nothing changes for existing quizzes), an error in `exam` as every quality rule on in `default`, `info` in `draft`; ignorable with `check-ignore`.
  - **Out of order:** one finding per section in `by-section`, one for the quiz in `by-quiz`, at the first question out of order: "Question 7 (truefalse) comes after a matching question; this quiz's order is single or multi, truefalse, matching or ordering, blanks, short, numeric or fields, code, essay", fix "move it, or change `type_order`". Ignoring that finding lets the next one show.
  - **Option `require`** (owner): `"by-section"` or `"by-quiz"`, no default. A quiz whose `type_order` is absent, `none`, or `by-section` where `by-quiz` is required gets one finding at its front matter (the `type_order` line when there is one): "this profile requires `type_order: by-section`; the quiz declares none", fix "add `type_order: by-section` to the front matter". `by-quiz` satisfies `require = "by-section"`: it is the stricter. A profile cannot set the order itself: the page and the paper follow the quiz, and a quiz must behave the same whoever builds it.
  ```toml
  [profiles.department-exam]
  extends = "exam"
  rules."questions.type-order" = { level = "error", require = "by-section" }
  ```
- **5. The key grouped by type** (owner, item 68; the headings **to approve**). On the key page the table of other questions becomes groups in the quiz's order (its `type_order` order, else the default, whatever the mode), each under a small heading ("Multiple choice", "True or false", "Matching and ordering", "Fill in the blanks", "Short answers", "Code", "Essays"; a custom group of several types takes the names of its types joined by "and"), in paper order inside a group; types outside the order last, under "Other". A group with no question is not shown. The grid's questions and the rubrics stay where they are; `inline` does not change.
